# Extended item transfers

Extended protocol revision 3 admits item transfers before changing private
ownership. Classic sessions retain their existing item commands and wire layout.

## Classic cursor drops

Classic multiplayer keeps a cursor item until its own drop command is applied.
If floor or delta capacity has filled in the meantime, the item stays in hand
and the player can retry. Another drop, inventory operation or level transition
waits while that ownership change is pending; changing the cursor cannot discard
it. A clean exit processes pending local drops before saving the hand.

These are local ownership protections using the existing classic commands, not
the distributed admission protocol below. They do not resolve every historical
classic replica disagreement or provide durable multiplayer world storage.
Single-player drops keep their immediate behavior.

## Admission and ordering

`CMD_ITEMTRANSFER` is appended to the command enum. Each request identifies the
actor, its slot generation, a monotonically increasing request number, the level,
the transfer kind and the existing little-endian `TCmdPItem` payload. The
coordinator assigns a session-wide serial and freezes the participating voters.
Initially slot 0 coordinates; an idle departure elects the lowest remaining ID.

1. The actor retains its hand, equipment or gold while requesting a transfer.
2. An offer reserves its item identity, delta capacity and, on loaded levels,
   floor capacity and destination tile. The recipient also reserves personal
   capacity. An occupied hand rejects a pickup without changing either item.
3. A private offer waits for the actor's original ordered request before voting.
   Buffered commands are flushed before item messages, so preceding equipment
   changes cannot arrive after the ownership change.
4. All required voters must accept. A rejection cancels the offer and releases
   reservations. Only the coordinator's ordered commit changes world state.
5. Every replica acknowledges application. The actor writes its updated profile
   before acknowledging. Finalization releases the operation; duplicate packets
   cannot apply it again.

The admission window holds 16 offers. The coordinator queues up to 1,032
requests (127 floor items, one private request and one monster reward per participant); replicas
can track 16 additional requests while offers are in flight. Deferred reward
creations are bounded to 254. Ordinary gameplay commands retain native batching.
Inventory operations wait while private ownership is unresolved; movement and
combat continue under the existing turn system.

## World capacity and generated items

Physical floor capacity remains 127. Extended deltas provide 254 records so
picked-up pregenerated items do not consume the records needed by a full floor
of later drops. Taken records are removed before dropped items are restored.

Replicated loot candidates remain hidden until admitted. Unoffered local
creations count toward generation capacity, preventing another burst from
reusing the same free slots while the coordinator responds. Only the original
publisher submits the generated item; local copies generated by replaying the
same monster or object action are discarded. Ordinary new loot still observes
the physical floor limit. Rejected mission/reward creations wait in shared
snapshot state and retry after a pickup frees space, including after an idle
publisher departure. A loaded participant still validates physical capacity
and terrain; rewards stay pending while everyone is on other levels. The
lowest active ID on the reward's level can propose a new valid position if the
original tile is occupied. The coordinator accepts only a position change to
an existing deferred operation, retaining its origin and item properties.
Replaying that proposal after completion cannot create another item.
Unique quest rewards can be prepared without a floor slot.
Owned death drops are different: failed admission retains equipment and gold
in the player profile rather than converting them into unowned rewards. Newly
split death-gold stacks mix the actor and slot generation into their seed so
clients sharing RNG state do not submit identical stack identities.

## Loading, leaving and persistence

Snapshots contain generations, serial watermarks, active offers and votes,
queued requests, and deferred reward descriptions. They are validated before
publication with the world delta. Reservations are reconstructed after loading
items, before buffered commands are replayed. Extended level transitions buffer
commands while grids are rebuilt.

A clean exit drains local ownership changes and waits for acknowledgements from
all peers. A peer acknowledges departure only after finalizing older transfers
that involve the departing player. This covers finalization and disconnect
messages arriving on different connections. A disconnect during an ambiguous
transfer ends the affected session instead of guessing a commit or rollback.
The multiplayer world remains ephemeral; this protocol is not durable world
storage or recovery from a failed disk write.

An optional `helditem` archive entry stores the cursor item with the existing
item codec, a record version and an edition byte. Saving an empty hand replaces
an older record. Loading never overwrites an occupied hand. `PlayerPack`,
single-player saves and vanilla classic saves retain their layouts. Older builds
ignore the optional entry and cannot restore a cursor item; put it in inventory
before using such a build. Multiplayer profile rewrites do not carry unknown
archive entries forward.

## Verification

`item_transfer_test` exercises independent replica state, reordered delivery,
replay, capacity contention, slot reuse, snapshots and departure barriers.
`multiplayer_gameplay_test` runs eight separate headless engines over production
TCP, with isolated profiles. It covers pickup rejection, simultaneous drops,
mission rewards, death, melee and projectile combat, bosses and shared pools.
The process runner is built on UNIX when TCP is enabled. These focused scenarios
do not replace full campaign, remote-network or cross-platform release testing.

## Monster reward decisions

Revision 3 also carries a validated monster reward identity in the existing item
payload. This kind reserves an encounter incarnation instead of floor/inventory
capacity. It uses the same ordered admission window, with one in-flight reward
per publisher. Every receiver waits for all voter fences before applying its
commit; later decisions and finalizations remain deferred in snapshots while
waiting. This settles damage contributors before XP, advances per-level loot
credits once, and stages resulting items through ordinary creation admission.
See [Extended party balance](extended-party-balance.md#synchronized-lifecycle).

Reward votes that overtake their offer on another connection are accumulated
by serial in a bounded 16-entry table. Offers fold those votes into their own
receipt set; snapshots preserve this table and restoration merges locally seen
early votes. This prevents a receiver waiting forever for a vote that arrived
before it knew the offer. The table adds at most 785 bytes to the junk snapshot,
within the existing 16-bit transfer limit.
